# Приоритетное сохранение косметики

## Найденная задержка

В обоих игровых профилях уже были установлены сборки с уведомлениями сайта.
Журнал 26.1.2 продолжал фиксировать таймауты личного API. Сохранение, фоновое
чтение комплекта и heartbeat работали последовательно в одной задаче. Поэтому
клик мог ждать окончания чужого сетевого запроса, включая его таймаут и повтор.

## Изменения модов 1.21.11 и 26.1.2

- Изменение комплекта отменяет ожидающее фоновое GET-чтение аккаунта.
  Его результат больше не занимает очередь сохранения. POST не отменяется:
  сайт мог уже начать или завершить запись.
- Heartbeat и выход выполняются отдельной задачей через отдельный HTTP-клиент.
  Зависший heartbeat не удерживает очередь сохранения.
- Планировщик сохранения проверяет работу раз в 25 мс. Группирование быстрых
  переключений сокращено со 150 до 40 мс; ограничение частоты — одна попытка
  в 500 мс вместо секунды. Уже выполняющаяся запись завершается прежде следующей.
- При быстрых кликах сохраняется последний комплект. Предыдущий POST не
  дублируется автоматически; конфликты ревизии обрабатываются прежним объединением.
- Heartbeat не может сбросить статус «сохранение» в «подключён»: подтверждение
  сохранения поступает только из личного API после ответа на запись.
- Уведомления сайта и совместимый обычный опрос сохранены.

## Изменения сайта

- Запись больше не загружает полные коллекции пользователей и всей косметики:
  для связанного профиля читаются только его строки.
- Снятые категории удаляются одним DELETE. Изменённые категории записываются
  одним пакетным UPSERT. Счётчик коллекции пересчитывается один раз и только
  при изменении количества строк. Всё выполняется в прежней атомарной транзакции.
- Повторный выбор уже сохранённого комплекта не переписывает строки, но
  повторно публикует актуальное состояние presence — в том числе пустой комплект.
- Выбор одной категории в браузере использует тот же путь записи, что и мод.
- После COMMIT сервер может подтвердить сохранение, не ожидая подготовки
  публичных уведомлений. Уведомления выполняются следующим проходом event loop,
  используют уже сохранённый комплект и объединяют повторные изменения аккаунта.
- Presence всех активных персонажей аккаунта обновляется одним UPDATE CASE
  вместо отдельной записи каждой строки. Heartbeat остаётся резервным обновлением.
- Проверки авторизации, каталога, ревизии и завершение COMMIT до подтверждения
  сохранены. Лимит записи увеличен до 240 запросов в минуту на аккаунт для двух
  одновременно работающих клиентов.

## Проверка и ограничения

Сборка обеих версий: `assemble -x test -x compileTestJava --offline --no-daemon`.
JavaScript проверяется на синтаксис. Автоматические тесты, пробные изменения
косметики на рабочем аккаунте и запуск Minecraft не выполнялись.

Полное время от клика до другого игрового кадра не измерено. 40 мс — пауза
группирования действий, а не обещание полной доставки за 40 мс. Задержка сети,
текущая запись и COMMIT базы данных остаются частью времени сохранения.
JAR необходимо обновить в обеих играх; запущенные процессы автоматически новый
код не получают. Папки установленных игр этим заданием не изменяются.
