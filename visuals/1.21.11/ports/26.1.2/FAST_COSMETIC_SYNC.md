# Ускоренная синхронизация — 1.21.11 и 26.1.2

Текущие параметры и дополнительные изменения очереди сохранения описаны
в `PRIORITY_COSMETIC_SAVE.md`. Ниже — первоначальная версия механизма уведомлений.

## Изменения модов

- Фоновый планировщик реагирует раз в 50 мс вместо ожидания секундного цикла.
  Проверка таймеров сама по себе не отправляет HTTP-запросы.
- После изменения комплекта выдерживается 150 мс без новых изменений.
  Затем отправляется последний выбранный комплект, включая снятые категории.
- При непрерывных переключениях отправка ограничена одним запросом в секунду;
  промежуточные состояния объединяются. Сетевой запрос, уже находящийся в работе,
  не прерывается. Это задержка планирования, а не гарантия полной доставки за 150 мс.
- Публичный список использует `/api/presence/watch` с ревизией. Сайт удерживает
  запрос, пока данные не изменятся, и отвечает сразу после изменения.
  При отсутствии изменений ответ приходит через пять секунд для подтверждения
  актуальности. Между запросами выдерживается 50 мс.
- Уведомление об изменении собственного комплекта вызывает внеочередное чтение
  сайта. Локальные несохранённые изменения сохраняют приоритет при объединении.
- Для старого сайта с HTTP 404 используется прежний опрос `/api/presence/online`.
  После сетевого сбоя действует двухсекундная задержка перед следующей попыткой.
- Сохранены отдельный транспорт публичного списка, обновление соединения при
  сбое, защита от устаревшей косметики и проверка контекста игрового мира.

## Изменения сайта

- Добавлен публичный read-only маршрут `/api/presence/watch?server=...&revision=...`.
  Он возвращает тот же список игроков и его SHA-256-ревизию.
- Сохранение комплекта из мода и выбор категории в браузере обновляют presence
  после завершения транзакции и уведомляют ожидающие клиенты.
- Heartbeat и выход также уведомляют об изменении состава списка. Ответ с
  неизменившимися данными не рассылается досрочно только из-за heartbeat.
- Публичные чтения фильтруют истёкшее присутствие SELECT-запросом без DELETE.
  Очистка старых записей выполняется при изменениях presence.
- Ожидания очищаются при закрытии соединения и ограничены 1000 запросами.
  Таймер не оставляет соединение открытым бесконечно.
- Лимит записи комплекта — 120 запросов в минуту на аккаунт; проверка авторизации,
  ID косметики и защита от конфликтов ревизии сохранены.

Требуется обновить JAR в обоих клиентах. Старый клиент продолжает работать через
совместимый маршрут, но не получает новый механизм ожидания событий.

Обе версии собираются `assemble -x test -x compileTestJava --offline --no-daemon`.
Автоматические тесты и запуск Minecraft не выполнялись. Сквозное время между
действием в одной игре и кадром второй игры не измерялось: оно также зависит
от задержки сети, сохранения на сайте и уже выполняющихся запросов.
