# Синхронизация двух версий: исправление задержек API

30 октября 2026, Minecraft 1.21.11 и 26.1.2.

## Найденная причина

Обе установленные сборки обращались к одному API и одному игровому адресу
`mc.deathmine.fun`. В обоих журналах были `HttpTimeoutException`. Подтверждённая
общая сессия сайта уже существовала; отсутствие входа не объясняло текущий сбой.

Журнал контейнера показал ответы `200` на heartbeat длительностью 5–7 секунд,
а также длительные запросы экипировки. Клиент ожидал ответ только 4 секунды.
Из-за синхронного адаптера MySQL обработка такого запроса задерживала и запросы
публичного списка. Вне Minecraft HTTPS-запросы также истекали по таймауту.

Горячие маршруты вызывали `visuals.account(user)`: полную сборку кабинета,
включая транзакцию профиля, друзей, подписки, платежи и конфиги. Это было лишним
для чтения шести косметических категорий.

## Изменения сайта

`visuals.equipped(user)` читает только косметику связанного профиля одним SELECT.
Чтение не создаёт профиль и не открывает транзакцию записи. Состояние раздела
и связь с аккаунтом учитываются в запросе. Этот метод используют чтение экипировки,
её ревизия и heartbeat. Авторизация и проверка прав при изменении не ослаблены.

Два файла (`lib/visuals.mjs`, `lib/visuals-client.mjs`) опубликованы на сервере
`affa700e`. Контрольные суммы удалённых файлов совпали с подготовленными.
Резервная копия:
`backups/before-presence-performance-2026-10-30T13-39-52-867Z.tar.gz`.

После публикации свежие серверные записи показывали чтение экипировки и presence
примерно за 80–530 мс вместо прежних секунд. Это наблюдение конкретных запросов,
а не нагрузочный тест и не гарантия постоянного времени ответа.

## Изменения модов

- Таймаут HTTP 15 секунд, подключения — 5 секунд. Сетевой обмен остаётся фоновым.
- Обычный опрос личного комплекта идёт через 5 секунд после окончания запроса,
  чтобы не создавать непрерывную очередь, если ответ задержался.
- Статус показывает число игроков из полученного API-списка.
- При изменении состава/косметики список имён и UUID записывается в INFO-журнал
  без токенов и идентификаторов аккаунтов сайта.
- Чужая косметика сначала сопоставляется по UUID. При переписанном сервером UUID
  допускается точное имя игрового профиля из текущего списка этого сервера.
  При неоднозначном имени этот запасной путь отключён. Пустые комплекты и выход
  очищают обе таблицы сопоставления.
- Своя локальная иконка не является подтверждением получения других игроков:
  для диагностики используются реальный список API и его число.

## Границы подтверждения

Обе версии собраны: `assemble -x test -x compileTestJava --offline --no-daemon`.
Автоматические тесты и запуск Minecraft не выполнялись. Файлы в установленных
`mods` не заменялись. Запущенные пользователем клиенты не перезапускались.

После уточнения пользователя, что оба клиента подключены, диагностический GET
30 октября в 13:47:23 UTC вернул HTTP 200 за 710 мс и **двух** игроков:

- `MrZakon`, версия 1.21.11, UUID `dc904498-8744-3314-beac-b7ae8c7c46ef`;
- `MrDanuul`, версия 26.1.2, UUID `e22ad869-3ec4-3e5b-8f82-a7c3643cef1e`.

У обоих опубликованы плащ 130 и рюкзак 36. Серверный журнал после обновления
подтвердил успешные heartbeat и получение списка от двух клиентов.
Таким образом, одновременное присутствие двух версий и публикация комплектов
подтверждены ответом рабочего API. Вид значков/косметики на экране обоих клиентов
в этой работе визуально не подтверждён.

Безопасные записи диагностики находятся в `.site-bridge/presence-performance`:
`console-after.json`, `roster-after.json`, контрольные суммы и исходные копии файлов.
